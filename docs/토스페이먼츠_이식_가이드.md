# 토스페이먼츠 이식 가이드

이 문서는 **웨딩 제품(spw-web)에 결제를 되살리는 문서가 아니다.**  
같은 기술 스택의 **다른 프로젝트**에, 이 저장소의 「결제 (토스페이먼츠)」만 옮길 때 쓴다.

웨딩 기능정의서는 결제·과금을 범위 밖으로 둔다. 이 저장소의 `api/src/payments/` 는 이미 삭제됐다.

공식 문서: [결제창 SDK v2](https://docs.tosspayments.com/sdk/v2/js) · [결제 승인 API](https://docs.tosspayments.com/reference) · [결제 취소](https://docs.tosspayments.com/guides/v2/cancel-payment)

---

## 1. 기술 스택 (이 저장소와 동일)

| 층 | 스택 | 이 저장소 경로 |
|---|---|---|
| 관리자 | Vite + React + TanStack Router | `admin/` |
| 사용자 | Next.js (App Router) | `user/` |
| API | NestJS + TypeORM | `api/` |
| DB | PostgreSQL 16, JSON은 `jsonb` | `docker/postgres/migrations/` |
| 키 저장 | `integration_configs` + AES-256-GCM | `api/src/integration-settings/` |

화면에서 토스 SDK를 직접 승인하지 않는다. **시크릿 키는 Nest만** 쓴다.

## 3. 키 관리를 먼저 이식한다

결제창보다 **연동 설정**을 먼저 옮긴다. 관리자가 키를 넣지 않으면 결제가 열리지 않게 한다.

1. `integration_configs` 테이블과 TypeORM 엔티티를 둔다.
2. `INTEGRATION_CONFIG_ENCRYPTION_KEY` 를 `.env.local` 에만 둔다. 커밋 금지. 운영은 필수.
3. `set()` 에서 값은 `encrypt()`, `get()` 에서 `decrypt()`. 시크릿 조회 API는 **마스킹**만 내려준다.
4. `KEY_META` 에 두 키를 등록한다.

```ts
TOSS_PAYMENTS_CLIENT_KEY: { category: 'PG', isSecret: false },
TOSS_PAYMENTS_SECRET_KEY: { category: 'PG', isSecret: true },
```

5. 관리자 화면: 클라이언트 키는 일반 `Input`. 시크릿은 `readOnly` + 「키 수정」.  
   저장 시 `isSecretMaskDisplay(value)` 이면 **기존 값을 덮지 않는다.**
6. 런타임은 `integrationSettings.get('TOSS_PAYMENTS_SECRET_KEY')` 로만 읽는다. `.env` 에 토스 키를 두지 않는다.

시크릿·paymentKey·orderId 를 로그에 남기지 않는다.

## 4. 결제 흐름 (권장 순서)

토스는 **브라우저에서 결제창 → 리다이렉트 → 서버가 confirm** 이다.  
프론트가 `paymentKey` 만으로 돈을 확정하면 안 된다.

```
관리자: CLIENT_KEY / SECRET_KEY 저장
        │
사용자: GET /payments/client-key          ← 공개, 시크릿 없음
        POST /payments/orders             ← 로그인 필요. orderId·amount 고정
        SDK v2 requestPayment(...)
        │
토스:   successUrl?paymentKey&orderId&amount
        │
사용자: POST /payments/confirm            ← 서버가 SECRET_KEY로 토스 confirm
        │
서버:   금액·주문자 재검증 후 기록 저장 + 상품 지급
```

실패는 `failUrl?code&message` 로 온다. 여기서 confirm 을 호출하지 않는다.

로컬은 **SDK v2** (`https://js.tosspayments.com/v2/standard`) 를 쓴다.  
v1 은 `127.0.0.1` Referer 검증으로 403 이 날 수 있다.  
토스 개발자센터에 결제 허용 도메인(`localhost`, 운영 호스트)을 등록한다.

## 5. API 설계 (Nest)

모듈은 `api/src/payments/` 한 곳에 둔다. 연동 설정 서비스를 주입한다.

### 5.1 `GET /payments/client-key`

인증 없이 클라이언트 키만 반환. 비어 있으면 빈 문자열.

```ts
const clientKey = await this.integrations.get('TOSS_PAYMENTS_CLIENT_KEY');
return { success: true, data: { clientKey: clientKey || '' } };
```

### 5.2 `POST /payments/orders` (회원 JWT)

상품을 서버에서 다시 읽고 **금액은 클라이언트를 믿지 않는다.**

- `orderId`: `[프로젝트접두]-[timestamp]-[random8]` (영숫자, 토스 제약 준수)
- 응답: `{ orderId, amount, orderName }`
- 주문을 **DB에 30분 TTL** 로 저장한다.  
  옛 구현은 `Map` 메모리라 프로세스 재시작·멀티 인스턴스에서 승인이 깨진다. 이식 시 테이블로 바꾼다.

### 5.3 `POST /payments/confirm` (회원 JWT)

바디: `{ paymentKey, orderId, amount }`

1. 주문 존재·만료·본인 여부 확인
2. `order.amount === amount` 아니면 400
3. `POST https://api.tosspayments.com/v1/payments/confirm`  
   헤더 `Authorization: Basic base64(secretKey + ':')`  
   바디 `{ paymentKey, orderId, amount }`
4. `ALREADY_PROCESSING_REQUEST` → 409
5. `orderId` unique 로 결제 행 저장 후 상품 지급
6. 주문을 소비 처리해 재사용 금지

### 5.4 관리자 취소

`POST https://api.tosspayments.com/v1/payments/{paymentKey}/cancel`

- 취소 전 `GET /v1/payments/{paymentKey}` 로 `balanceAmount` · `isPartialCancelable` 확인
- `Idempotency-Key` 헤더
- 가상계좌 환불은 `refundReceiveAccount` 필요
- 토스 취소가 된 뒤 지급분 회수가 실패하면 **수동 보정** 로그를 남긴다 (금액은 로그에 넣지 말고 내부 id만)

## 6. 사용자 화면 (Next)

1. 마운트 시 `GET /payments/client-key`. 없으면 「관리자가 연동 설정에서 키를 등록」 안내.
2. 결제 버튼 → `POST /payments/orders` → SDK 로드 → `TossPayments(clientKey).payment({ customerKey })`.
3. `customerKey` 는 회원당 고정 문자열. 접두사는 새 프로젝트 이름을 쓴다 (`vcut-` 재사용 금지).
4. `requestPayment`:

```ts
await payment.requestPayment({
  method: 'CARD',
  amount: { value: order.amount, currency: 'KRW' },
  orderId: order.orderId,
  orderName: order.orderName,
  successUrl, // 예: https://.../payments/complete
  failUrl,
  customerName,
  customerEmail,
})
```

5. complete 페이지는 쿼리의 `paymentKey` · `orderId` · `amount` 로 **한 번만** confirm.  
   `sessionStorage` 로 새로고침 중복 호출을 막고, 서버는 unique `orderId` 로 멱등을 보장한다.

## 7. DB (PostgreSQL)

키 테이블은 기존 `integration_configs` 를 그대로 쓴다.

결제 기록 예 (크레딧이 아닌 주문에도 컬럼명만 바꿔 쓰면 된다):

```sql
CREATE TABLE payments (
  id              BIGSERIAL PRIMARY KEY,
  user_id         INT NOT NULL,
  order_id        VARCHAR(120) NOT NULL UNIQUE,
  payment_key     VARCHAR(200) NOT NULL,
  amount_krw      INT NOT NULL,
  refunded_amount_krw INT NOT NULL DEFAULT 0,
  status          VARCHAR(20) NOT NULL DEFAULT 'completed',
  created_at      TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  cancelled_at    TIMESTAMPTZ NULL
);
```

주문 대기는 별도 `payment_orders` (`order_id` unique, `expires_at`, `user_id`, `amount_krw`) 를 권장한다.

마이그레이션은 `docker/postgres/migrations/V00N__*.sql` **새 파일만**. 적용된 버전은 수정하지 않는다.

## 8. 구현 순서

1. **연동 설정 PG 탭** — 키 저장·마스킹·암호화. 관리자에서 테스트 키를 넣고 목록에 클라이언트 키가 보이는지 확인.
2. **`GET /payments/client-key`** — 사용자 화면에서 키를 받는지 확인. 시크릿이 응답에 없는지 확인.
3. **주문 테이블 + `POST /orders`** — 금액은 서버 상품 기준.
4. **결제창 SDK v2** — 토스 테스트 카드로 successUrl 까지.
5. **`POST /confirm`** — 토스 승인 후 DB 저장·상품 지급. 금액 조작 요청은 400.
6. **fail 페이지** — confirm 호출 없음.
7. **관리자 취소** — 테스트 결제 전액 취소. 부분 취소는 `isPartialCancelable` 가드.
8. 운영 키로 바꾸기 전, 토스 콘솔 허용 도메인·웹훅(쓸 경우)을 확인.

## 9. 검수

- [ ] 시크릿 키가 브라우저 네트워크·콘솔·서버 로그에 없다
- [ ] 관리자가 마스크 상태에서 저장해도 시크릿이 `***` 로 덮이지 않는다
- [ ] 클라이언트가 `amount` 를 바꿔 confirm 하면 거절된다
- [ ] 같은 `orderId` 로 confirm 을 두 번 해도 이중 지급이 없다
- [ ] 로컬은 `localhost` + SDK v2. `127.0.0.1` 만 쓰면 막힐 수 있다
- [ ] 테스트 키(`test_`)와 라이브 키를 섞지 않는다

## 10. 새 프로젝트에서 바꾸면 되는 이름

| 옛 이름 (vcut) | 새 프로젝트 |
|---|---|
| `customerKey`: `vcut-{userId}` | `{앱}-{userId}` |
| `orderId` 접두 `vcut-` | 앱 접두 |
| 지급 대상 `creditsService.grant` | 구독·이용권·주문 상태 등 그 제품의 도메인 |
| 회원 `JwtAuthGuard` + `userId` | 그 프로젝트의 회원 JWT. 관리자 JWT와 섞지 말 것 |

토스 시크릿을 화면·`NEXT_PUBLIC_*`·AI 서버에 넣지 않는다.
